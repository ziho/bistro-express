# Bistro Express

两个人的私人点餐小馆：一方提交每一餐想吃什么（在家做 / 去餐厅），主厨维护菜品与餐厅，并通过 Bark 收到新建、修改、取消的推送。

- 前端：React + Vite + TypeScript（`/bistro/` 子路径，PWA）
- 后端：Hono on Node，SQLite（better-sqlite3），单容器双监听
  - `3000` 公开监听：只提供访客界面与访客 API，所有 `/bistro/admin*`、`/bistro/api/admin*` 一律 404
  - `3001` 内部监听：管理后台 + 访客功能，仅发布到 `127.0.0.1:8787`
- 数据：`./data`（SQLite + 图片），不进 git；没有备份功能

## 店铺编辑与统一分类

- **前台入口**只控制店铺出现在哪儿：出街食 / 饮番杯，可都选；分类不会自动改变入口。
- **分类标签**是唯一需要维护的分类，菜系、餐品、口味和场景都填在这里。例如日料、咖啡、蛋糕、约会，可多选、自定义、搜索或复用已有标签。店铺最多 24 个标签；菜品仍为 12 个。
- 店铺编辑默认显示店名、前台入口、分类标签和一句话点评；位置与地图、菜单与相关链接、预算与备注、照片分组收起，并显示已有内容摘要。保存会保留未展开的资料；校验错误会展开相应分组并聚焦字段。
- 前台和后台共用标签与地区筛选，不再维护独立的饮品甜品类型。快捷分类与完整筛选使用同一套标签，支持任一 / 全部符合；“未分类”现在指未填任何标签的店铺。后台仍先筛选全部店铺，再按每页 10 家分页，改变筛选后回到第一页。
- 启动时执行迁移 9：把原店铺类型补入标签，已有对应名称或明确别名的不会重复添加；不改入口、更新时间、照片、链接、历史计划快照或通知。旧 `treat_types_json` 列及接口字段仅作兼容缓存，实时从标签推导。清空标签不会从旧缓存恢复分类；旧客户端显式提交的类型会转换成追加标签。
- 批量导入同样只编辑标签和入口。旧导入草稿中的类型会合入标签；尚未确认的提交保留原请求编号和正文，重试不会重复导入。本机旧类型筛选会转成可见标签，不留下无法清除的隐藏条件。

### 统一管理店铺标签

- 在「店铺 → 标签管理」查看所有标签、关联店铺数和上架数，支持按现名或旧名搜索，每页 20 个。可重命名单个标签，或勾选多个标签合并到一个现有名称或新名称。
- 提交前先「查看影响」，核对受影响的店铺、下架数量和重复标签；确认后一次更新全部相关店铺，同一家店只保留一个相同标签。期间若相关资料发生变化，需要重新预览；网络中断可用同一次请求重试。
- 旧名称作为别名保留：日后手工填写、旧页面保存或批量导入旧名时，自动改用统一名称。后台和前台的标签筛选也会跟着更新，包括本机记住的筛选；已打开的页面每 30 秒在前台刷新目录，或刷新页面立即获取。
- 本次仅管理店铺标签；菜品标签和历史安排快照保持原样。迁移 10 只新增 `venue_tag_aliases` 表，不自动合并已有分类，也不改动现有店铺内容。

## 首次部署

```bash
# 1. 生成 .env（公网入口日期只以 scrypt 哈希保存，后台免密码）
PUBLIC_BASE_URL=https://share.zihoh.com/bistro \
ADMIN_BASE_URL=https://whitepc.tail913bc.ts.net:8788/bistro \
npm run setup            # 按提示输入入口日期（YYYY-MM-DD），也可用 BISTRO_ENTRY_DATE=… 或 stdin 传入

# 2. 构建并启动（需要已存在的外部网络 1panel-network）
docker compose up -d --build
docker compose ps        # 健康检查：/bistro/api/health
```

反向代理：公开站点把 `/bistro/` 转发到 `bistro-express:3000`（示例见 `ops/nginx-location.conf`）；管理入口把私有 HTTPS 地址转发到 `127.0.0.1:8787`。

## 日常运维

```bash
docker compose logs -f bistro-express          # 查看日志
docker compose up -d --build                    # 更新代码后重新部署（启动时自动执行数据库迁移）
docker compose restart bistro-express           # 重启
BISTRO_ENTRY_DATE=YYYY-MM-DD npm run setup      # 修改入口日期，之后重启容器
```

后台入口 `/bistro/admin` 是一个简单的欢迎页，点「进入」到「概览」：这里列出餐厅、菜品、计划、通知和推送设置的入口及简要数量。各管理页面（如 `/bistro/admin/restaurants`）仍可直接打开，顶部的 Bistro 标志可回到欢迎页，后台内的未知地址会回到欢迎页。

首次进入后台后：在「推送设置」里打开总开关、添加 Bark 设备并发送测试推送；在「菜品」「餐厅」添加内容（初始目录为空）。未配置推送时，通知会显示为「通知未配置」，配置后可在「通知」页一键重试。

升级到多设备版本时，启动会自动执行数据库迁移 2：旧的单个设备 Key 会变成一台名为「原设备（旧版单设备设置）」的设备（总开关与服务器地址保持不变），已有通知记录原样保留。`.env` 不需要改动。

后台通过 Tailscale 私有入口直接访问，应用不再要求管理密码。内部监听仍只映射到本机回环，公开监听和公网 Nginx 继续拒绝所有管理路径。公网点餐的日期验证保持不变。

## 功能说明

### 首页选日期

- 日期条只显示最近 7 天（今天、明天……），有安排的日子带小圆点。
- 「选择日期」按钮打开站内月历（手机上是底部弹层），不依赖系统日期控件：周一开头，可上/下个月、按年份/月份跳转、直接输入日期（如 `2027-03-05`、`2027年3月5日`），「回到今天」一键返回。
- 过去的日子不可选（历史计划在「历史」页查看）；所有即将到来的有效计划日期都会在月历上标记，不再只标前 10 天。
- 键盘：方向键按天/周移动，Home/End 到周一/周日，PageUp/PageDown 换月（加 Shift 换年），Enter 选择，Esc 关闭。
- 选中 7 天以外的日期时，日期会显示在「选择日期」按钮上，下方列表和「加一餐」都使用该日期。

### 家常菜：菜单分区、主料与采购提醒

- 新建菜品只有「菜名」必填，其余都可以不填；照片上传和「做法链接」保持原样。
- **菜单分区**（`sections`，可多选，也可不选）：建议分区为「配饭菜」「饭面简餐」「汤羹」「小食甜品」，也可以添加自定义分区；其他菜已经用过的分区（包括旧的「家常」等分类）会作为可点选项出现。每道菜最多 8 个分区，每个最多 60 字（与旧分类上限相同，旧值都仍然有效），保存时去掉首尾空格、合并连续空格并去重。分区只用于分菜单；口味、场景等描述继续写在「标签」里，两者互相独立。
- **主料**（`ingredients`，最多 20 行）：每行是 `{ name, quantity, purchaseNote }`，即主料名称（最多 40 字）、用量（最多 60 字，自由填写如「半盒」「一把」「约300g」「适量」，不做单位换算）、采购提示（最多 160 字，如「去骨鸡腿」「嫩豆腐」「常买品牌」，服务器不会访问任何链接）。只是几样主要材料，不代表完整配料表；三项都空的行会被忽略，填了用量或采购提示却没写名称会报这一行的错误。
- **总耗时 / 动手时间**（`totalMinutes` / `activeMinutes`，整数分钟 0–1440）：都可以不填（`null`），也可以只填一个；`0` 会被保存为 0，不等同于未填。两者都填时动手时间不能超过总耗时。不会自动推算。
- **份量**（`servingText`，最多 60 字，如「一盘（两人分享）」「一人份」）和**采购提醒**（`shoppingNote`，整道菜的采购备注，最多 300 字）：自由文本，未填为空字符串。
- 后台表单中，分区、介绍、做法链接和标签直接显示；主料、耗时、份量和采购提醒收在「主料、耗时与采购」里，编辑已有这些信息的菜时会自动展开。新表单每次都会提交全部字段，所以清空某项（`[]` / `null` / `''`）就会真的清除。
- 点菜页与后台列表都是文字卡片：完整换行显示菜名，下面是分区、主料简表和耗时/份量；没有照片时不显示占位图，有照片时显示小缩略图。卡片本身用于加入/取消，「详情」是单独的按钮，详情里只显示实际填写过的内容。按分区筛选时，同时属于两个分区的菜在两个分区下都能找到；没有分区的菜在「全部」里照常显示。搜索会匹配菜名、分区、标签、介绍、主料名称和采购提示。
- 新计划保存时会冻结每道菜当时的分区、标签、介绍、做法链接、主料、耗时、份量和采购提醒，之后修改或下架菜品都不会改变已保存的计划；计划详情里每道菜都可以展开查看这些冻结的信息。
- 升级时自动执行迁移 5：只新增列（`sections_json`、`ingredients_json`、`total_minutes`、`active_minutes`、`serving_text`、`shopping_note`，默认空值），不重建表、不改动已有的更新时间；每道菜原来非空的「分类」原样（仅规整空白）成为它唯一的分区，不拆分、不改名、不归入新的建议分区，名称、标签、介绍、照片和做法链接都不变。旧的 `category` 列保留，之后保存菜品时会让它等于第一个分区（没有分区时为空），所以清空的分区不会因为重新执行迁移而恢复；接口仍返回只读的 `category`（第一个分区）给旧页面使用。
- 兼容旧页面：只提交 `category`（没有 `sections`）新建菜品时，非空分类会成为一个分区；同时提交 `sections` 时以 `sections` 为准（`[]` 表示不分区）。旧页面编辑菜品时不会提交新字段，这些字段保持原值；它提交的空分类或菜品已有的分区不会改动分区，提交新的分类只替换第一个分区，其余分区保留。
- 旧计划的原始快照不改写，也不会去读取当前菜品：读取时没有分区信息的旧快照用当时的分类作为分区，其余新字段为空；快照里显式的空分区列表不会被旧分类覆盖。

### 在家吃：共享采购清单

每一餐「在家吃」都有一份两人共享的采购清单，由这一餐冻结的菜品快照里的**主料**和手动补充项组成。它只是提醒要买什么，不是库存：服务器不记录家里存货、不扣减数量、不做单位换算或相加、合并清单项时不识别同义词，也不会从备注文字里推断「已有」。（每台设备可以在本机记下现有食材作为提示，见「按现有食材找菜」，它不会自动改变清单。）

- **合并规则**：主料名称只在去掉首尾空格、合并连续空格、忽略英文大小写后完全相同时才合成一项（`Egg` = `egg`）；标点、写法和同义词都保持分开（「番茄」≠「西红柿」，「嫩豆腐」≠「老豆腐」）。合并后的每一项逐条保留每道菜原来的用量和采购提示，并标明来自哪道菜：两道菜各写「2颗」就是两条「2颗」，不会变成一条，也不会相加。没填的用量/提示不显示，不会补占位。
- **顺序**：按第一次出现的顺序排列（菜按这一餐的顺序、主料按菜谱里的顺序，然后是手动补充）；同一项里先列菜谱来源，再列手动补充。
- **整道菜的采购提醒**（`shoppingNote`）单独列出并带菜名，不会变成清单项或状态。没有记录任何主料的菜（包括只写了采购提醒的菜）会在提示里按菜名列出；旧计划的快照没有主料时清单就是空的并显示这个提示，不会编造食材。
- **状态**：每一项只能是「待采购」「家里已有」「已买好」之一，随时可改回；「家里已有」表示够这一餐用。数量按**食材种类**统计。待采购的项排在前面；家里已有/已买好的收在可展开的「已准备好」里，可移回待采购。每个状态按钮都是明确的三选一（不是开关），读屏会读出食材名。
- **手动补充**：保存后的这一餐可以手动加要买的东西：名称必填（最多 40 字），数量（最多 60 字）和备注（最多 160 字）可选，每餐最多 50 项。保存时去掉首尾空格并合并连续空格；超长会报错，不会截断。和菜谱同名的补充会并入同一项并标明「手动补充」；手动补充可单独编辑或删除，菜谱里的主料只能在后台改菜谱。
- **编辑点菜页的预览**：选了菜之后，点选菜标题旁的「采购清单」或已选内容里的「采购清单预览」（手机上会先关掉已选内容弹层再打开预览），查看按当前菜品合并的清单。预览是只读的（「保存这一餐后，可标记状态和补充采购项」），不会给提交加额外步骤，状态和补充项也不会存进本机草稿。

需求变化时的规则（计划修改在同一个数据库事务里同步清单，读取时从不写库）：

- 每一项保存一个「需求签名」：来源身份（菜品 id / 手动补充 id）、每条原始用量、采购提示、所在菜的整体采购提醒。签名与顺序无关、保留重复出现；菜名或主料名的大小写/空格改写不算变化。
- 修改这一餐时：新出现的项是待采购；被移除的项连同状态一起删除（以后再加回来也从待采购开始，不会恢复旧状态）；签名没变的项保留状态（只调整菜或主料的顺序不会重置）；签名变了（用量、采购提示、来源增减、手动补充的增删改）的项重置为待采购；之前已标为家里已有/已买好的项会显示「需求已变化，请重新确认」，可重新设置状态或确认仍待采购。
- 改成「去餐厅」会清空这一餐的手动补充和全部状态，之后再改回在家吃也不会恢复。「再来一顿」生成的新计划从全部待采购、没有手动补充开始。
- 已取消或已经过去（按计划时区）的这一餐，清单保留可看（含状态），但不能再改；去餐厅的计划没有采购清单。

多设备与接口：

- 状态和补充项存在服务器上，两台设备共享。没有实时推送：打开计划页、切回页面时会重新获取，页面在前台时每 30 秒刷新一次，也可以点「刷新」。
- 修改都是「先保存成功再显示」：保存中会显示「保存中…」，失败会说明原因并保留输入；网络中断时可点「重试」，用同一个请求编号重发同一请求，不会重复添加。离线时只能查看。
- 编辑补充项在独立弹层中进行，打开时记录所依据的清单版本。后台刷新、食材移入已准备好区域不会关闭表单或清空输入；发生冲突时保留输入并提示核对当前记录，再次保存才确认修改。其他设备删除该项或餐单变成只读时仍保留弹层内容，但不能提交。自己的请求保存期间锁定输入，避免成功后清空刚刚继续输入的新内容。
- 改清单**不会**改变这一餐的版本号和保存时间，也**不会**发送 Bark 推送；新建/修改/取消这一餐的通知规则不变。
- 接口（与计划接口同样需要公网日期验证或内部监听，校验 `Origin`，请求体上限 64 KiB；所有写请求都需要 `Idempotency-Key`，同一编号重发相同内容返回第一次的结果，内容不同返回 422）：
  - `GET /bistro/api/plans/:id/shopping` → `{ planId, planVersion, revision, writable, lockReason, items, manual, dishNotes, dishesWithoutIngredients, counts, updatedAt }`；`items[]` 为 `{ key, name, sources, status, needsReview }`，来源 `sources[]` 为 `{ kind: 'dish', dishId, dishName, name, quantity, purchaseNote }` 或 `{ kind: 'manual', manualId, name, quantity, note }`。
  - `PUT …/shopping/status`：`{ key, status: 'pending' | 'have' | 'bought', expectedPlanVersion, expectedRevision }`。
  - `PUT …/shopping/have`：`{ keys: string[], expectedPlanVersion, expectedRevision }`，把几项待采购一次标为「家里已有」（见下文「按现有食材找菜」）。`keys` 至少 1 个、不能重复、最多 650 个；全部成功或全部不改：有不在清单里的项返回 404 `shopping_item_missing`（`details.missingKeys`），有已经是家里已有/已买好的项返回 409 `shopping_item_not_pending`（`details.changedKeys`），两者都带 `details.current`。成功只增加一次修订号。
  - `POST …/shopping/manual`（201）、`PUT …/shopping/manual/:manualId`：`{ name, quantity?, note?, expectedPlanVersion, expectedRevision }`；`DELETE …/shopping/manual/:manualId`：`{ expectedPlanVersion, expectedRevision }`。只能改/删指定编号的手动补充。
  - 每次写都要带上读到的这一餐版本（`expectedPlanVersion`）和清单修订号（`expectedRevision`，从未写过时为 0；每次成功写入 +1，与这一餐的版本号相互独立）。任一不符返回 409（`plan_changed` / `shopping_conflict`），错误详情 `details.current` 是最新清单，页面据此刷新并提示重新确认；已取消/已过去/去餐厅返回 422 `shopping_locked`；找不到项或手动补充返回 404；超过 50 项返回 422 `manual_limit`。
- 数据：升级时自动执行迁移 6，只新增一张 `plan_shopping` 表（`plan_id`、`revision`、`manual_json`、`states_json`、时间戳），不改动任何已有的表、计划快照或时间戳。从没改过清单的计划没有对应行，读取时按快照直接算出全部待采购，不会写库；第一次改状态或补充时才创建这一行。

### 在家吃：按现有食材找菜

点菜页「今天在家吃什么」上方的「按现有食材找菜」可以展开/收起。收起时点菜页和以前完全一样；展开但还没记下食材时，只提示先添加，不判断、不隐藏任何菜。

- **记下现有食材**：只存在这台设备的浏览器里（`localStorage` 的 `bx:pantry`，带版本号），**从不上传**，服务器上没有库存，也不记录数量、保质期或扣减。可以一次输入或粘贴多样，用逗号、中文逗号、顿号、分号或换行分开；回车加入（输入法选字时的回车不会提交），Shift + 回车换行。输入时会提示菜单里已有的食材名称。最多 100 样，每样最多 40 字，一次最多粘贴 8000 字：超出的名称不会被截断或丢掉，而是留在输入框里并说明原因；已经记下的会提示「已经在清单里」。可以逐个移除或清空，显示上次更新时间。退出登录会和草稿一起清除。
- 存储被禁用或已满（如无痕模式）时会提示，清单仍可在当前页面使用，只是关闭后不保留；读到格式不对的数据时提示无法读取、按空清单显示，下次修改时覆盖。同一浏览器的其他标签页会自动同步。
- **怎么算匹配**：名称去掉首尾空格、合并空格、忽略英文大小写后相同，或属于下面这几组明确的同义词才算同一样：番茄 = 西红柿、土豆 = 马铃薯、西兰花 = 青花菜、香菜 = 芫荽、卷心菜 = 圆白菜 = 包菜、黄瓜 = 青瓜、荸荠 = 马蹄。不做包含、模糊或智能匹配：豆腐 ≠ 嫩豆腐 ≠ 老豆腐，牛肉 ≠ 肥牛 ≠ 牛肉末，辣椒 ≠ 小米辣 ≠ 青椒。同义词只用来判断「有没有」，**不会**合并采购清单的项、改名或改动任何已保存的状态和快照（采购清单里「番茄」「西红柿」仍是两项）。
- **每道菜**按记录的主料**种类**判断：全部都有是「主料齐了」，否则「还缺 N 种」，没记录主料是「暂时无法判断」。只看名称，不核对数量；记录的主料也可能不完整。卡片上列出已有和还缺的名称，「详情」里逐项列出原来的用量和采购提示。
- **筛选与排序**：全部 / 主料齐了 / 还缺 1 种 / 还缺 2 种 / 暂时无法判断（各带数量），可再加「总耗时 30/60/90 分钟以内」（没记录总耗时的菜不会出现在时间筛选里）。和搜索、分区、标签、「已选」筛选叠加使用。排序：主料齐了 → 缺得少 → 已有得多；一样都没有的排在后面，无法判断的排最后；相同时保持菜单原顺序。
- **采购清单预览**（未保存的这一餐）：记下了现有食材时，预览分成「还需采购」和「家里可能已有」两部分，每项来源、用量、提示照旧完整显示；只是提示，不写入任何状态。
- **已保存的这一餐**：如果有待采购的项出现在记下的现有食材里，采购清单会显示「核对后标记家里已有」。打开后逐项列出这些食材和每条用量/提示，默认全部勾选，需要明确确认「够这一餐用」才会提交；不会因为记下了就自动标记，已经是家里已有/已买好的项不受影响，之后修改记下的食材也不会改变已保存的状态。只发送勾选项的编号（`PUT …/shopping/have`），从不发送整份现有食材。
  - 打开时记下清单的版本和修订号；期间被其他设备改过时提交会被拒绝（409），弹层保留勾选、显示最新内容，需要再确认一次才会按新版本提交。网络中断时可「重试」，用同一请求编号重发，不会重复写入。离线、其他修改正在保存、这一餐已取消/已过去/改成去餐厅时不能提交，但勾选保留。
  - 和其他清单修改一样，不改变这一餐的版本号和保存时间，也不发送 Bark 推送。

### 添加到日历

已保存、未取消的每一餐（在家吃和去餐厅都有）在计划详情里有「添加到日历」：

- **Google 日历**：打开预先填好的 Google 日历新建页面，需要在 Google 日历里确认保存。**Apple / 其他日历（.ics）**：下载一个日历文件，在日历应用里打开确认。应用无法知道是否真的添加成功，所以只显示「已打开 / 已准备好文件」。不使用日历授权、订阅或任何外部写入。
- 两种方式由同一个事件生成器生成，内容一致，全部来自这一餐保存时冻结的信息（不读当前菜单）：
  - 有具体时间：从保存的时间点开始，时长固定 60 分钟（跨午夜、夏令时切换都按真实的 60 分钟），按这一餐自己的时区解释，不受查看设备时区影响；文件里用 UTC 时间，Google 链接带上原时区。没有具体时间：那一天的全天日程（结束日期为第二天，不含）。
  - 标题如「晚餐 · 在家吃」「晚餐 · 店名」；地点是餐厅地址（没有地址时用店名），在家吃是「在家」；说明里有菜名或餐厅、地图链接、备注、原时间和时区、计划详情链接、编号和版本。不含采购清单状态，不加提醒（按日历自己的默认提醒）。
- 之后在这里修改或取消**不会**同步到日历，需要手动调整；重复添加可能产生重复日程（同一餐的 .ics 使用相同 UID，部分日历会更新而不是重复）。已取消的这一餐不显示入口；已经过去的这一餐仍可导出一次，标明只读。
- Bark 推送的链接不变（打开计划详情）。新推送的正文末尾加一行提示：新建「可在计划详情里添加到日历」，修改「如已添加到日历，请手动更新日程」，取消「如已添加到日历，请手动删除日程」。已有的通知记录不改写，也不会多发推送。
- 接口：`GET /bistro/api/plans/:id/calendar.ics`，和其他计划接口一样需要公网日期验证或内部监听（没有公开链接或令牌链接）。返回 `text/calendar; charset=utf-8`、`Content-Disposition: attachment; filename="bistro-<编号>.ics"`、`Cache-Control: private, no-store`；Service Worker 不缓存。单个 VEVENT：`UID` 为 `<计划 id>@bistro-express`（每个计划固定），`SEQUENCE` 为这一餐的版本号，`DTSTAMP` 为保存时间（读取从不写库，同一版本每次下载内容相同），CRLF 换行、按 75 字节折行（不拆开 UTF-8 字符），逗号/分号/反斜杠/换行按 RFC 5545 转义，用户填写的内容不能插入新的日历行。计划不存在或编号无效返回 404，已取消返回 422 `calendar_unavailable`。文件里的计划链接指向发起下载的入口（公网或内部地址）。

### 餐厅：点评、标签和菜单链接

- 餐厅采用文字卡片，完整换行显示店名；没有照片时不显示占位图，有照片时保留小缩略图。
- 后台用「一句话点评」（最多 160 字）记录推荐理由，用「分类标签」统一分类。一家店可有多个标签，多家店可复用同一标签；输入空格或逗号分隔，也可点选已有标签。原有长备注保留。
- 「相关链接」每家店最多 8 个（菜单、官网、订位页面等），每个都有可自定义的显示名称（最多 20 字，如「看菜单」「访问官网」「订位」），不填名称时显示「查看链接」。只接受完整的 http(s) 网址（不能带账号密码、空格或控制字符），名称填了而网址空着会提示错误，两项都空的行会被忽略。链接只在新窗口打开，服务器不会访问或嵌入链接内容。
- 后台每条链接可用「上移 / 下移」调整位置，保存后前台依次显示；第一条不能上移，最后一条不能下移。旧计划保留保存时的链接顺序。
- 选餐厅卡片直接显示前 2 个链接，其余的用「还有 N 个链接」进入餐厅详情查看；餐厅详情和已保存计划显示全部链接。地图链接单独保留。点击链接不会改变候选名单。
- 升级时自动执行迁移 3，将旧「菜系」合并到标签，保留已有标签、备注与餐厅数据。旧计划原始快照不改写，读取时兼容；新计划保存当时的点评、标签与链接。
- 升级时自动执行迁移 4：新增 `links_json` 列，把每家店原有的单个链接（网址 + 按钮文字）转成链接列表的第一项；旧列保留不删（不重建表），之后在后台保存该餐厅时旧列会被清空，因此删除的链接不会因为重复执行迁移而恢复。旧计划快照不改写：没有链接列表的旧快照读取时沿用其原来的单个链接，显式的空列表就是没有链接。新计划保存时冻结当时的全部链接。旧版本页面仍提交单个 `linkUrl`/`linkLabel` 时会被转换为一项链接；同时提交 `links` 时以 `links` 为准（`[]` 表示清空）。

### 餐厅：从 Google 地图链接填写（仅后台）

在「添加餐厅」里粘贴 Google 地图分享链接，点「识别链接」，结果只会填进表单，**不会自动创建餐厅**；核对后仍需点「保存」。

- 不使用任何 API Key 或付费 Places API，只解析链接本身：`/maps/place/<店名>`、`q`/`query`、`query_place_id`、`cid`、`ftid`、`data=` 里的 `!1s` 地点编号和 `!3d…!4d…` 店铺坐标（区分 `@lat,lng` 地图视角中心）。
- `maps.app.goo.gl`、`goo.gl/maps` 短链接由服务器展开：只允许 https 的 Google 地图主机，拒绝用户名/端口/IP/localhost，逐跳校验、最多 5 次跳转、总超时 8 秒，不读取网页内容。只请求短链接（以及完全不含地点信息的 `maps.google.com/maps?…` 旧链接），跳到 `www.google.com/maps/…` 后直接解析、不再请求；每 10 分钟最多识别 150 次（单个添加和批量导入共用，够一批 100 个链接加重试）。
- **能填的只有店名和地图链接**（跟踪参数会被去掉；也可改用原始短链接）。地址、点评、标签、菜单链接、预算、照片、评分、营业时间都不会自动获取——Google 分享页面本身不提供这些（实测标题只是「Google Maps」），请手动填写。
- 已经手动输入的店名/链接不会被覆盖，需要点「用识别结果替换」才会替换。
- 若链接里的地点编号（CID/FTID/Place ID）或原链接与已有餐厅相同，会提示「可能已经添加过」；同一品牌的不同分店不会被当成重复。旧餐厅保存的短链接不会被展开，只能按链接本身比对。
- 识别失败（短链接失效、跳转到 Google 同意/登录页、网络问题）时，粘贴的链接会保留，可继续手动填写。

### 餐厅：批量导入（仅后台）

「餐厅」页右上角的「批量导入」（`/bistro/admin/restaurants/import`）用于一次收藏 20–100 家店。只需要店名和地图链接，地址、点评、照片等之后在普通编辑里补充。

1. **粘贴**：每行一个 Google 地图链接（短链接、`google.com/maps` 地点链接，或带店名的分享文字都可以），一次最多 100 个非空行。超过 100 行、单行超过 2048 字符或整段太长时整批拒绝并说明原因，不会截断；没有链接或不是 Google 地图链接的行会留在队列里并标出原因。再次粘贴会追加到队列末尾，已有的行和修改保持不变；队列里待导入的行最多 100 行。
2. **识别**：浏览器逐行调用已有的「识别链接」接口，同时最多 2 个请求，每行显示进度；可随时暂停/继续。遇到 429 会立即暂停并显示需要等待的秒数，未识别的行保留，等待结束后需手动点「继续识别」，不会自动重试。识别只填空着的或仍是上次自动填入的店名/地图链接，手动改过的店名和任何标签都不会被覆盖。
3. **核对**：每行可修改店名、标签、地图链接和原始链接。改了原始链接或地图链接后需点「重新识别」；识别失败的行可单独重试或「重试全部失败」。如果短链接暂时展开不了，但它本身是有效的 https Google 地图链接，可以勾选「直接用这个链接和我填写的店名导入」。
4. **标签**：「批量添加标签」把输入的标签（可点选已有标签）合并去重后加到已选的行；已导入的行和已有餐厅不受影响。每行最多 12 个标签、每个最多 16 字，超出上限的行不修改并提示。
5. **导入**：只有识别成功（或明确选择手动导入）、字段有效、且不重复的行才能被选中。「导入已选的 N 家」一次提交到私有接口 `POST /bistro/api/admin/restaurants/import`，结果逐行显示：新增的行变为只读、不会再次导入；重复和出错的行保留，修改后可再试。导入不会产生任何通知。

重复检查：

- 只按链接和地点编号判断（原始链接、去掉跟踪参数后的地图链接、Place ID / FTID / CID / 地点编号、同名且同一坐标），**从不只按店名**，同一品牌的不同分店不算重复。已有餐厅包括已下架的；队列里后出现的同一地点会提示「和第 N 行是同一个地点」。重复的行默认跳过，不提供强制导入。
- 服务器在导入时会用最新数据库重新检查，并检查同一批里先导入的行；检查和写入在同一个 SQLite IMMEDIATE 事务里，并发的两次导入不会同时插入同一家店。浏览器传来的识别结果和重复判断都不被信任：服务器离线重新校验严格的 https Google 地图链接（导入时不访问任何网址），尽量保存去掉跟踪参数的地图链接，短链接原样保存。
- 已知限制：已保存的短链接不会被展开。如果某家店当初保存的是短链接 A，再用另一个短链接 B 导入同一家店，B 展开后的地点编号无法和 A 对上，所以不会被识别为重复；用同一个短链接 A 或已保存完整链接时可以识别。

草稿与重试：

- 队列（含识别结果和修改）只保存在当前浏览器标签页的 sessionStorage 中：刷新或离开本页不会丢失，关闭标签页后清除；不会保存到服务器。读取时校验版本和格式，异常的草稿会被丢弃并提示。
- 每次导入带一个 Idempotency-Key，提交前先把请求内容和编号存进草稿。网络中断或没收到答复时，这一批会锁定并提示「重新提交」：用同一编号和完全相同的内容重发，服务器返回第一次的结果，不会重复创建；同一编号配不同内容会被拒绝（409）。不确定结果时也会刷新餐厅列表。
- 离开页面时正在识别的请求会被取消，这些行下次进入时仍是「等待识别」；正在导入时离开，回来后可「重新提交」确认结果。识别或导入进行中关闭/刷新标签页时浏览器会提示确认。

限制：导入接口每次最多 100 行，只对这一条私有路由放宽请求体上限到 1 MiB（超出时可减少本批行数再提交），其余接口仍是 64 KiB；公开监听上该路由同样是 404，所有写请求照常校验 `Origin`。

### 店铺：全球地区与用途（吃饭 / 饮品甜品）

后台的「餐厅」现在显示为「店铺」（接口路径仍是 `/restaurants`）。每家店多了两项：

- **地区**（`location`，全部可选）：`country`（国家/地区，通常是中文，如「加拿大」）、`region`（省/州，有英文时用英文，否则用当地写法；城市国家如新加坡可以不填）、`city`（城市，按实际所在填写：Burnaby 就是 Burnaby，不会归到 Vancouver），以及 `countryCode`（两位 ISO 代码，如 `CA`，可为空）和 `source`（`osm` = 和 OpenStreetMap 建议完全一致，`manual` = 手动填写或改过，`''` = 没填）。不假设任何行政层级，不会从店名、地址、标签、IP 或地图视角推测地区；没有全局城市词典，可选项只来自已有店铺用过的值。
- **用途**（`purposes`，至少一项）：`meal`（吃饭）和/或 `treat`（饮品甜品）。同一家店两样都卖时两个都勾，不需要建两条。用途是结构字段；「奶茶、甜品、雪糕、蛋糕、咖啡、面包、川菜、火锅、约会」等仍然写在可自定义的标签里。
- 校验：去掉首尾空格并合并连续空白；国家 ≤40 字、省/州和城市各 ≤60 字；含控制字符、零宽或双向控制字符会被拒绝；国家代码必须是已知的两位代码，只填代码时自动填中文国家名，改了国家名而没带代码时旧代码会被清掉。
- 兼容旧页面：新建时不传就是「地区未知 + 吃饭」；**修改时不传 `location` / `purposes` 会保留原值**（旧页面不会把饮品甜品店改回吃饭）；`location` 里某个字段传 `''` 就清空该项，`location: null` 清空全部；`purposes: []` 会被拒绝（400）。
- 卡片和详情显示简短的「国家 · 省/州 · 城市」和用途；来自 OpenStreetMap 的地区旁会注明「© OpenStreetMap contributors」并链接到版权页。

### 喝点 / 吃点甜的（独立的饮品甜品安排）

- 首页每天有「加一餐」和「喝点 / 吃点甜的」两个入口；编辑页「安排什么」有三选一：在家吃 / 去吃饭 / 饮品甜品。饮品甜品是一次独立的安排（自己的日期、时间、备注、候选、抽签、Bark 推送、日历），**不挂在某一餐下面**。
- 数据：`plans.mode` 仍是 `home | restaurant`，新增 `purpose: 'meal' | 'treat'`（在家吃永远是 `meal`；在家吃传 `treat` 返回 422 `invalid_purpose`）。旧客户端新建不传 `purpose` 就是吃饭；**修改时不传会保留原来的用途**。
- 只显示适合当前用途的店（同时有两种用途的店两边都有）；服务器在新建和修改时都会拒绝不适合的候选（422 `incompatible_purpose`，`details.restaurantIds`）；随机抽签只在适合当前用途、仍上架的候选里抽。
- 切换用途时，如果有不适合的候选，会先弹出确认，列出将被移出的店（和已抽中的结果），确认后才移出；已选的菜不受影响，在家吃 ↔ 去店里切换时草稿内容照旧保留。
- 新的饮品甜品安排名字为空时默认「下午茶」，自己写的名字不会被改；快捷名称换成「下午茶、咖啡、奶茶、甜品、宵夜甜点」。
- 计划卡片、详情、确认弹层、本机草稿、历史、Bark 推送（标题如「新的饮品甜品安排」，正文「饮品甜品：店名」「地区：…」）和日历（标题「下午茶 · 店名」、说明「饮品甜品：店名」）都按用途显示，不会把饮品甜品叫成「用餐」；首页「接下来」里饮品甜品会标注出来。日历仍是固定 60 分钟 / 全天，.ics 接口和保护方式不变；取消、改期、「再来一顿」和正餐完全一样（再来一顿会去掉已经不适合该用途的店）。两种外出安排都没有采购清单。
- 保存时冻结店铺当时的地区和用途；之后改店铺不会影响已保存的计划。旧计划的原始快照不改写，读取时没有地区/用途的旧快照显示为「地区未知 + 吃饭」，不会从当前店铺补全。
- 本机草稿新增 `purpose`；旧草稿读取时视为吃饭，并且仍按旧格式（不带 `purpose`）重发未确认的提交，保证同一个 Idempotency-Key 的请求内容完全一致。

### 店铺筛选：多标签、地区、用途

- 点餐页和后台店铺列表用同一套筛选（`shared/venueFilter.ts`）：搜索（店名、点评、地址、备注、预算、标签、国家/省州/城市）、标签、地区、用途、「已选」之间都是「并且」。
- **多标签**：默认「符合任一」（日料 或 烧烤），可切换为「全部符合」（日料 并且 约会）。标签多时可以在筛选里搜索，显示已选个数。
- **地区**：按「国家 → 省/州 → 城市」选择，可以多选（任一符合），选国家或省/州包含其下所有城市；同名城市按完整路径区分（British Columbia 的 Richmond ≠ Virginia 的 Richmond）；「未填地区」也可以单独筛选。选项只来自已有店铺的数据，不做在线自动补全。
- 手机上点「筛选」打开底部弹层，改完点「查看 N 家」才生效，可「清除全部」；宽屏是可展开的内联面板，改动立即生效。已启用的条件以可单独移除的标签显示在搜索框下方。筛选不会改动候选名单。
- 点餐页会在本机记住上次的标签、模式和地区（`localStorage` 的 `bx:venue-filter`，带版本号，吃饭和饮品甜品分开记；已经不存在的标签/地区会被忽略；存储不可用时就不记）。它和草稿分开保存，退出登录时一起清除，不会上传。

### 地区识别（OpenStreetMap Nominatim，仅后台）

- 在添加/编辑店铺时点「从地图链接识别地区」，或在「识别链接」/批量导入的识别中顺带识别。只用链接里**店铺自己的坐标**（`/maps/place/…` 的 `!3d…!4d…`，或本身就是一对坐标的链接）做一次反向地理编码；`@lat,lng` 地图视角、按店名搜索的链接、只有 Place ID / CID 没有坐标的链接都不会查询，会提示手动填写。不抓取 Google 网页，不使用店名、IP 推断。
- 建议只填入空着的项或上次自动填入且没改过的项；手动填写的值会保留，并显示「用建议替换」按钮。识别失败或关闭时都不影响店名/地图链接的识别，也不阻止导入。
- 遵守 [Nominatim 使用政策](https://operations.osmfoundation.org/policies/nominatim/)：只在用户点击时查询（启动、后台、定时都不会查询；已有店铺不会被自动查询）；服务器全进程共用一个队列（公开/内部监听共用），同一时间最多 1 个请求、两次请求开始间隔至少 1.1 秒，相同的等待请求合并；排队上限 20、单次超时 10 秒、响应最多 64 KiB、不跟随任何跳转；带标识 `User-Agent: BistroExpress/1.0 (+<公网地址>)`；请求格式 `format=geocodejson&layer=address&zoom=10&accept-language=en`。
- 结果保存在 SQLite 的 `geo_cache` 表（按服务地址 + 语言 + 精确到 5 位小数的坐标），成功结果（包括「这里查不到」）缓存 90 天，重启后不会重复查询；失败不缓存，可手动重试。只使用服务实际返回的国家、省/州（`state`）和城市（`city`，或结果本身就是 city/town/village 时的名称），不会把 county、district 当作城市；国家名由 ISO 代码通过 `Intl.DisplayNames('zh-CN')` 得到，没有中文名时保留服务返回的英文名。
- 「推送设置 → 地区识别」可以开关或改为其他 Nominatim 兼容地址（存在 SQLite 设置里，无需改代码或 `.env`）；正式配置默认开启公共服务。修改设置会丢弃排队中的请求，不同服务的缓存互不混用。测试环境默认关闭，所有测试都用假的响应和时钟。接口：`GET/PUT /bistro/api/admin/geo/settings`（`{ enabled, baseUrl }`），`POST /bistro/api/admin/restaurants/resolve-map-link` 新增可选 `geo: true`，返回 `geo: { status: 'suggested' | 'no_point' | 'not_found' | 'unavailable' | 'disabled', … }`；公开监听上同样一律 404。
- 使用到建议数据的地方都会注明「© OpenStreetMap contributors」并链接 <https://www.openstreetmap.org/copyright>。公共服务没有可用性保证，可能限流或临时不可用。

批量导入的补充：

- 每行可以填写国家、省/州、城市和用途（默认吃饭）；正在排队或识别地区的该行会等结果返回后再允许导入，服务失败不阻止导入；中断后重进可继续识别。工具栏可选「识别链接时同时识别地区」（默认开启）。地区识别不到会单独显示，不算链接识别失败；可逐行「重新识别地区」或「重试失败的地区」，使用同一个服务器队列和限流，不会自动无限重试。
- 修改原始链接或地图链接会作废这一行还没返回的地区结果（迟到的结果不会覆盖），并清掉上次自动填入且没改过的地区。
- 「批量填写地区和用途」：对已选的行，「填入空白」只填空着的项，「覆盖已选行」才会改掉已填的值；用途可一键设为吃饭、饮品甜品或两者。
- 浏览器草稿升级为第 2 版：第 1 版的队列仍能读取（地区为空、用途为吃饭），等待确认的那一批按原样（同一编号、同样内容）重新提交。服务器导入时逐行校验地区和用途，错误只影响这一行；重复判断仍只看链接和地点编号，不看店名、地区或用途。

升级时自动执行迁移 7：只新增列和一张缓存表——`restaurants` 的 `country`、`country_code`、`region`、`city`、`location_source`（默认空）和 `purposes_json`（默认 `["meal"]`），`plans.purpose`（默认 `meal`），以及 `geo_cache`。不重建表、不改 `mode` 的约束、不改动任何更新时间、标签、备注、计划快照或通知；旧店铺全部是「吃饭 + 地区未知」，不会推测城市或标签。

已知限制：地区识别依赖链接里带店铺坐标（短链接展开后通常有），只有 Place ID 的链接需要手动填写；Nominatim 返回的行政区划可能和日常叫法不同（请核对）；国家名称的中文写法取决于运行环境的 ICU 数据；地区筛选按文字比较（忽略大小写和多余空格），「Canada」和「加拿大」会被当成两个国家，请复用已有的写法。

### Bark 多设备推送

- 「推送设置」里有总开关和共用的 Bark 服务器地址（默认 `https://api.day.app`，可填自建服务器），以及最多 10 台设备：名称、打码的 Key、单独启用/暂停、编辑、删除、单台测试和「测试全部启用的设备」。
- Key 只存在服务器私有 SQLite 中，任何接口、日志和错误信息都只显示打码后的 Key；同一个 Key 不能重复添加（也可以粘贴 `https://api.day.app/<key>/…` 整段地址）。
- 每次新建/修改/取消计划，所有启用的设备都会收到同一条推送。每台设备单独记录送达结果、单独重试（最多 5 次）：一台失败不会让已送达的设备重复收到。
- 重试期间停用或删除的设备会被标记为「已跳过」；事件发生后才添加的设备不会收到这条旧通知的重试。只有完全没送达任何设备的通知（例如当时未配置），手动重试时才会发给当前启用的设备。
- 只要有设备没收到，通知就不会显示为全部送达：访客看到「部分送达（1/2 台设备）」，后台「通知」页点开一条记录可逐台查看设备名、状态、尝试次数和错误。计划被再次修改时，旧版本未送出的推送会被新版本取代。
- 服务重启时正在发送的那一台设备可能收到重复推送（每条都带编号和版本号）。

### 通知记录（分页 + 保留 14 天）

- 后台「通知」页每页 10 条，按创建时间从新到旧排列；每行只显示标题、时间、类型、计划编号和状态，点开后在弹层里看各设备送达情况、错误和推送正文。当前页码写在地址里（`/bistro/admin/notifications?page=2`），翻页时保留上一页内容直到新页加载完成，加载中的旧行不可操作。
- 「重试全部未送出（N）」和概览里的「N 条待处理」统计的是保留期内所有页，不只是当前页；单条重试和全部重试都只重发未送达的设备，同一时间只允许一个重试请求。
- 只保留最近 14 天（按通知创建时间，精确滚动 14×24 小时；正好 14 天的保留，更早的删除）。服务启动时（先恢复中断的发送，再清理，然后才开始投递）和之后每小时清理一次，**永久删除**过期的通知记录及其逐台设备记录，不做归档或备份；计划、设备、设置、菜品、店铺和采购清单都不受影响。计划的通知记录被删除后，计划详情只是不再显示通知状态。
- 正在发送中的记录不会被删除，下一轮清理再删；超过 14 天还没送出的记录即使尚未被清理，也不会再自动发送或被手动重试（返回 `409 expired`）。
- 接口（仅内部监听，公开监听一律 404，写操作仍校验 Origin）：`GET /bistro/api/admin/notifications?page=1&pageSize=10` 返回 `{ items, page, pageSize, total, totalPages, held, retentionDays }`。`page` 和 `pageSize` 必须是不带符号、小数或前导零的正整数（`pageSize` 最大 50，`page` 最大 100000），否则 400；超过最后一页时返回最后一页（没有记录时为第 1 页、`totalPages` 为 1）。不带参数时仍返回旧版数组（最多 200 条，同样只含保留期内的记录）。数据库无需迁移。

### 界面动效

参考 [Emil Design Engineering](https://github.com/emilkowalski/skills/blob/main/skills/emil-design-eng/SKILL.md)、[Apple Design](https://github.com/emilkowalski/skills/blob/main/skills/apple-design/SKILL.md) 和 Apple 的 [Designing Fluid Interfaces](https://developer.apple.com/videos/play/wwdc2018/803/)，保留小馆配色，用原生 CSS / Web Animations API 实现，不增加动效依赖。

- 弹层进入约 260ms，退出 160ms，使用快速响应、逐渐减速的自定义曲线；手机版从底部出现，桌面轻微缩放。遮罩一起淡入淡出，关闭后立即归还焦点、停止拦截点击，可直接打开下一个弹层；快速重开表单会开始新的编辑会话。支持 display/overlay 离散过渡的浏览器有退场过渡，旧浏览器直接关闭。
- 「在家吃 / 去吃饭 / 饮品甜品」的选中底片连续滑动；日历切月 150ms；Toast 进入 220ms、退出 160ms；页面切换和通知翻页仅 120ms 淡入。通知自动刷新、搜索输入不会重播页面动效，翻页后定位并聚焦新列表。
- 运动以 transform / opacity 为主；只在精细指针设备上提供卡片 hover 微位移。键盘触发的交互立即完成，并终止本应用正在运行的反馈动画；系统「减少动态效果」关闭位移和缩放，仅保留很短的淡出，偏好变化在当前页面立即生效。

## 安全要点

- 公网访客：输入正确日期后获得 30 天会话。令牌随机生成、仅哈希存库，Cookie 为 `HttpOnly; Secure; SameSite=Lax; Path=/bistro`。
- 后台：连接 Tailscale 后直接进入，无需密码或管理 Cookie。权限由内部监听端口决定；伪造 Host、转发头或旧管理 Cookie 均不能在公网取得管理权限。旧管理密码配置不再使用，初始化也不再生成管理密码。
- 公网日期验证有按客户端 + 全局的失败次数限制；包括后台在内的所有写请求仍校验 `Origin`。
- 菜单、计划、图片都需要会话；Service Worker 只缓存公开外壳与静态资源，从不缓存 API/图片
- 上传支持 JPEG/PNG/WebP/HEIC，统一转为去除 EXIF 的 WebP（长边 1600 + 480 缩略图），不接受 SVG
- `.env`、`data/`、`secrets/` 均已 gitignore；`.env.example` 只含占位值
